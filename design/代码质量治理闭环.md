# 代码质量治理闭环

## 目标

代码质量结论必须来自可复现证据，而不是角色对“优雅”的主观表态。控制面负责顺序、
证据完整性、返工和升级；业务仓库负责生成机器可读质量报告。

## 流程

```text
Architecture -> Critic -> Development -> quality_gate -> Review -> Software QA
                                  |             |
                                  +-- reject ---+
                                         -> Development
```

1. Developer 提交 `implementation`、`test_evidence`，进入 `quality_gate`。
2. 业务仓库运行 local/branch/pr 质量场景并生成完整 JSON。
3. JSON 作为 `quality_report` artifact metadata 挂到当前 requirement。
4. 控制面自动读取 `passed`、blocking result、`infra_error`、findings、债务摘要和豁免。
5. 通过后才能进入独立 Reviewer；代码失败退回 Development；基础设施失败停在门禁。
6. Reviewer 驳回必须提供结构化 findings；修复后所有 Development 证据重新生成。
7. Review 通过后进入 Software QA。QA 只验证行为、合同和回归，不评价代码风格。

可直接用 CLI 挂接业务仓库生成的报告：

```bash
python3 scripts/control-plane.py artifact attach \
  --project-id <project-id> \
  --requirement-id <requirement-id> \
  --kind quality_report \
  --uri /absolute/path/to/artifacts/ci/quality-gates-pr.json \
  --metadata-file /absolute/path/to/artifacts/ci/quality-gates-pr.json
python3 scripts/control-plane.py workflow advance <requirement-id> --actor quality-automation
```

## 质量报告契约

artifact metadata 是完整 `quality_gate_report/v*` 对象，至少包含：

```json
{
  "schema_version": "quality_gate_report/v1",
  "scenario": "pr",
  "passed": true,
  "results": [
    {
      "name": "code_quality_incremental",
      "status": "passed",
      "blocking": true,
      "owner": "architecture",
      "details": {
        "findings": [],
        "debt_summary": {"added": 0, "reduced": 1, "unchanged": 12},
        "active_waivers": [],
        "expired_waivers": [],
        "invalid_waivers": []
      }
    }
  ]
}
```

每个 finding 应包含 `rule_id`、位置、baseline、current、delta、责任域、建议动作和
waiver 状态。只有 `blocking=true` 的失败影响 Review 准入；report-only 结果保留为债务证据。

## Reviewer 与返工

Reviewer 的 `findings` 必须是列表。blocking finding 至少包含：位置、`rule_id`、风险、
证据、最小修复建议和状态。存在 open blocking finding 时不能 `pass`。

质量门或 Reviewer 驳回后，requirement 回到 `development`。控制面以驳回时间为证据
新鲜度边界，旧 `implementation`、`test_evidence`、`quality_report` 和 `review` 不能复用。
同一 stage 第三次驳回时自动进入 Owner Inbox，由 Owner 选择继续、缩小范围或取消。

## PM 交付摘要

`delivery_summary` artifact metadata 必须包含：

```json
{
  "quality_summary": {
    "debt_added": 0,
    "debt_reduced": 1,
    "active_waivers": [],
    "residual_risks": []
  }
}
```

PM 只核对结构化门禁和风险归属，不亲自裁决代码是否“足够优雅”。

## 运行时与角色文件

角色核心模板不包含固定 agent ID、本机路径或 tmux 假设。运行
`scripts/build-agent-files.sh` 时，根据 `execution_surface` 追加 `codex_app` 或 `tmux`
overlay。修改模板后必须重建 `agents/*/AGENT.md` 与 `CLAUDE.md` 并运行生成回归测试。
